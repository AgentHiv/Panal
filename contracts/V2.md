# Panal v2 — Dual MON + $PANAL escrow

Panal v2 extends the v1 protocol (hardened post-audit) with dual-currency support:
tasks paid in **native MON** (`currency == address(0)`) or in the **$PANAL** token (ERC-20).

- $PANAL token on mainnet: `0x2e2e44e7fa6178822d4397299f719e89d1a67777` (18 decimals, 1B supply, EIP-1167 proxy)
- PanalReputation v1 on mainnet: `0xadAd5582B2023aAE7a89d42d6aF0B530c6C3e4D6` (**not reused** — see Migration)

## Contracts

| Contract | File | Notes |
|---|---|---|
| PanalRegistryV2 | `src/v2/PanalRegistryV2.sol` | A fresh registry with a `currency` per agent (at the end of the struct) |
| PanalEscrowV2 | `src/v2/PanalEscrowV2.sol` | Dual-currency escrow, accounting per token |
| PanalReputation | `src/PanalReputation.sol` | **Unchanged** — a **new instance** is deployed for v2 |

## Differences vs v1

### PanalRegistryV2
- `Agent` adds `address currency` (`address(0)` = native MON) **at the end of the struct**:
  `(owner, metadataURI, pricePerTask, active, registeredAt, currency)`. The first 5 fields keep
  their v1 ABI positions, so a v1 decoder of `getAgent` still works (it ignores the extra field);
  there's a test that checks it.
- Constructor `constructor(address _panalToken)`: sets an immutable `PANAL_TOKEN`.
  If `_panalToken != address(0)` it requires `code.length > 0`. If it's `address(0)`, the registry
  stays in MON-only mode.
- `registerAgent(metadataURI, pricePerTask, currency)` and `updatePrice(newPrice, currency)` check
  that `currency == address(0) || currency == PANAL_TOKEN`.
- The `AgentRegistered` / `PriceUpdated` events include `currency` (new topics: v1 indexers must be
  updated).
- The rest of the ABI stays: `updateMetadata`, `setActive`, `getAgent`, paginated `getAgents`,
  `getAgentCount`, `isActiveAgent`.
- `pricePerTask`/`currency` are **informational**: the escrow never reads them on-chain (the client
  sets the amount). Changing currency with active tasks doesn't affect existing tasks, which complete
  in their original currency (LOG-08).

### PanalEscrowV2
- `Task` adds `address currency` (at the end of the struct; the `tasks(i)` tuple = the 8 v1 fields +
  `currency`).
- `createTask(worker, taskHash, deadline, currency, amount)`:
  - **Native MON**: like v1, the client freely sets the amount via `msg.value` (v1 does NOT read the
    price from the registry); `amount` must be `== msg.value` and
    `msg.value >= MIN_TASK_AMOUNT_NATIVE` (0.001 ether, as in v1).
  - **$PANAL**: `msg.value` must be 0; the client must `approve(escrow, amount)` and the contract does
    `transferFrom(client, escrow, amount)`. `balanceOf` is measured before/after and **what was
    actually received** is recorded as the task's `amount` (fee-on-transfer defense, R-02); it reverts
    if what was received is `< MIN_TASK_AMOUNT_TOKEN` (1e18 = 1 $PANAL).
  - `worker != msg.sender`: self-tasks aren't allowed (LOG-03); nor can you claim (`claimTask`) a task
    you created yourself. A Sybil with 2 addresses is still possible: reputation is a soft metric,
    weigh counterparty diversity off-chain.
  - `nonReentrant` (R-03): there's no longer any function that moves funds without the guard.
  - Any other `currency` reverts (`unsupported currency`).
- 100% per-currency accounting: `pendingWithdrawals[token][user]` (`token == address(0)` = MON),
  `withdraw(token)` with CEI + `nonReentrant`; the 2.5% fee is charged **in the task's own currency**.
- A manual SafeERC20 (the same style as v1's manual ReentrancyGuard, zero-dependency): low-level
  wrappers that accept tokens that don't return `bool`.
- Constructor `constructor(registry, reputation, treasury, arbitrator, panalToken)` with `code.length`
  guards, a `registry.PANAL_TOKEN() == panalToken` check (`token mismatch`) and
  **`reputation.escrow() == address(0)`** (`reputation already consumed`): it's impossible to deploy an
  orphan escrow against a reputation whose one-shot `setEscrow` was already used (LOG-02).
- `openDispute` only from `Status.Delivered` (LOG-06): before delivery the client already has
  `cancelTask` and the worker has nothing to dispute — instant claim+dispute griefing is removed.
- Every other v1 flow is identical, respecting `task.currency`: `claimTask`, `deliverResult`,
  `approveAndRelease`, `autoRelease`, `resolveDispute`, `cancelTask`, `resolveStuckDispute`,
  `setTreasury`, `transferArbitrator` (arbitrator-or-owner), `transferOwnership`.
- `DISPUTE_TIMEOUT = 14 days` and `AUTO_RELEASE = 3 days` unchanged.
- Events: `TaskCreated` and `Withdrawal` include the currency; the rest are as in v1.

### Design decisions
- **Task amount**: v1 uses a free `msg.value` (the registry price is informational, it's not read
  on-chain). v2 replicates that model: the client sets the amount — `msg.value` for MON, `amount` for
  $PANAL.
- **Reputation**: the contract is v1 unchanged, but a new instance is deployed (see Migration).
  `totalEarned` mixes MON and $PANAL units (both 18 decimals): it's an **informational nominal
  multi-currency sum, not a value in a single unit of account** (LOG-09/R-07). Don't use it to rank
  agents; derive per-currency metrics off-chain from the `CompletionRecorded` events.
- **A single allowed token**: only the `PANAL_TOKEN` set at deploy (immutable). Adding more tokens
  requires v3.
- **No sweep of trapped funds** (R-04, a deliberate decision, parity with v1): MON forced in via
  `selfdestruct`/coinbase or tokens sent to the escrow by accident stay trapped with no rescue. The
  expected amounts are dust; adding a safe sweep (only the surplus over obligations) is left for v3.
- **Arbitrator liveness (LOG-05)**: timeout resolution is biased towards the client — if there's an
  active dispute and the arbitrator doesn't resolve it within `DISPUTE_TIMEOUT` (14 days),
  `resolveStuckDispute` (permissionless) refunds **100% to the client** and the worker gets 0 even if
  it delivered. A mandatory operating runbook:
  1. A monitor of `TaskDisputed` events with an immediate alert to the arbitrator.
  2. A resolution SLA of **< 14 days** from `disputedAt` (visible on-chain).
  3. If the arbitrator is going to be inactive, `transferArbitrator` to a backup key **beforehand**
     (the current arbitrator or the owner can do it).
  4. The arbitrator can't lock funds for more than 14 days (the timeout is the valve), but their
     absence makes the client the automatic winner of any dispute.

## Migration plan (v1 → v2)

1. **RegistryV2, the (new) PanalReputation and EscrowV2 are deployed fresh** (there's no migration of
   v1 agent/task/reputation state; v1 tasks in progress finish their cycle in the v1 escrow, which stays
   operational but unused).
2. **A NEW PanalReputation is deployed** (same v1 code) and the script sets
   `newReputation.setEscrow(escrowV2)`. Why not reuse v1's?
   - The mainnet v1 reputation already used its one-shot `setEscrow` with the v1 escrow
     (`escrow() != address(0)`, verified on-chain): reusing it would always revert.
   - **No real history is lost**: the v1 escrow has `getTaskCount() == 0` on mainnet, so the v1
     reputation is empty (no completion recorded).
3. Agents re-register in RegistryV2 choosing a currency (MON or $PANAL).
4. The frontend/pointers switch to the v2 addresses.

## Deploy

```bash
cd contracts

# Testnet (Monad testnet, chain id 10143): export the testnet token address
export PRIVATE_KEY=0x...
export PANAL_TOKEN=0x...   # $PANAL token on testnet
export TREASURY=0x...      # optional (default: deployer)
export ARBITRATOR=0x...    # optional (default: deployer)

forge script script/DeployV2.s.sol:DeployV2 \
  --rpc-url https://testnet-rpc.monad.xyz \
  --broadcast --verify

# Mainnet (chain id 143): PANAL_TOKEN has a mainnet default
# (0x2e2e44e7fa6178822d4397299f719e89d1a67777), exporting PRIVATE_KEY is enough
# (+ TREASURY/ARBITRATOR if they differ from the deployer):
forge script script/DeployV2.s.sol:DeployV2 \
  --rpc-url https://rpc.monad.xyz \
  --broadcast --verify
```

The script deploys RegistryV2 → PanalReputation (new) → EscrowV2 and runs
`reputation.setEscrow(escrowV2)` in the same broadcast, logging the 3 addresses (+ treasury/arbitrator).
The reputation is born fresh (`escrow == 0`, owner = deployer), so the final `setEscrow` can't fail,
and EscrowV2's constructor checks `reputation.escrow() == 0`: if any step reverts, the whole script
reverts and no orphan escrows are left. (Note: with `--broadcast` the deployments are independent
transactions mined in order; if the script is aborted halfway by an external failure, retrying redeploys
everything from scratch — contracts deployed without the final `setEscrow` are inert and unusable, not a
funds risk.)

## Tests

```bash
forge test            # full suite (v1 + v2)
forge test --match-path "test/v2/*" -vv   # v2 only
```

- `test/v2/PanalRegistryV2.t.sol` — a port of the v1 tests + dual currency (invalid currency, currency switch, constructor).
- `test/v2/PanalEscrowV2.t.sol` — a port of the v1 tests in native MON + new guards (amount mismatch, token mismatch,
  EOA token, dispute only after delivery).
- `test/v2/PanalEscrowV2Dual.t.sol` — $PANAL flows: exact approve, no approve (revert), 2.5% fee in PANAL,
  withdrawal isolation per currency, full dual flow, minimums per currency, dispute/resolution and
  `resolveStuckDispute` in PANAL, mixed ratings.
- `test/v2/AuditFixesV2.t.sol` — the v2 audit's fixes and PoCs as permanent tests:
  self-task blocked (create + claim), constructor with a consumed reputation (revert), fee-on-transfer
  recording the net amount (and the minimum on what was received), reentrancy in `createTask` blocked by
  `nonReentrant`, `getAgent` decodable with the v1 ABI, dispute+timeout biased to the client (LOG-05,
  documented), cosmetic currency switch (LOG-08), trapped forced MON (R-04, accepted), fee math without dust.
- `test/v2/PanalReputation.t.sol` — a port of the v1 tests (contract kept as is).
- `test/v2/mocks/MockERC20.sol` — an 18-decimal ERC-20 with public mint (zero-dependency).
- `test/v2/mocks/MockFeeOnTransferERC20.sol` — token mocks with a 5% fee and a token with a callback (R-02/R-03 tests).
